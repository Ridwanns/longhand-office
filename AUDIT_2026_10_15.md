# Quant source and run-state audit

15 October 2026 · local Office and rebuilt static browser edition.

## Verified defects fixed

### Automatic IDX eligibility and execution used different sources

The automatic ticker desk checked the published Yahoo catalogue for an eligible model cutoff, then submitted an ordinary local run. The local worker interpreted IDX as Flowless. The reported BBCA run therefore acquired289 eligible Flowless observations and correctly failed the350-observation requirement even though Yahoo's published BBCA history had363 eligible observations. The eligibility check and execution did not refer to the same source.

Automatic ticker requests now retain an explicit `historySource: published-yahoo` selection. The Node worker reads one complete matching published Yahoo file from the local public-data directory, checking the manifest/file identity, market, currency, listing, acquisition vintage and completion flags. It retains the original retrieval timestamp and adjustment definition, plus a separate file-load timestamp/hash. It does not splice providers or fetch MSN history. US automatic runs use the same explicit published source too.

Custom settings expose the source choice in Advanced settings. Existing requests without a source keep their earlier default: live Yahoo for US, Flowless for IDX. Reload and rerun retain the explicit selection. Legacy config hashes remain unchanged when the source field is absent or the default blank form option is selected. Export validation rejects a published-Yahoo run that instead declares Flowless provenance.

The failed saved run remains unchanged. Its local recovery action **Try published Yahoo history** creates a different run ID using the same ticker, cutoff, basis, seed and horizon. It never lowers the350-observation threshold. If the requested source is absent or insufficient, the new run fails explicitly too.

### Simple view concealed run failures and direct-link status

Simple mode intentionally hid detailed core charts, but that also hid the actual failed/cancelled/running state. Opening a saved run without a matching local ticker study could show an empty brief with no visible reason for failure.

A concise status section now remains visible in either view. It identifies the run's ticker/source, exact failure or progress, and completed sample/date. Completed runs offer **Open model detail** through the existing Advanced navigation. Failed runs expose retry actions; unaccepted submissions expose their retained draft's **Retry request** rather than a button requiring a nonexistent saved run. Changing the ticker clears the preceding run notice immediately.

### A late poll could replace a newly selected ticker's run

A controlled delayed-response test reproduced the old BBCA response overwriting the result object and status for a new AAPL request before its submission finished. The page's active run ID belonged to AAPL while its loaded run/ticker belonged to BBCA.

Starting a new run now invalidates earlier polling immediately. Both successful and failed poll callbacks also verify the panel's current run ID after awaiting the server. A previous submission's completion can no longer clear the newer submission's busy state. The delayed-response regression now leaves the new ticker and its pending state intact.

## Remaining limits

These are scoped regression checks, not a proof that every possible bug or provider failure is absent. Published Yahoo histories are dated snapshots and some tickers lack sufficient uninterrupted data. An older cutoff can still be ineligible. Flowless and Yahoo have different adjustment definitions and remain distinct sources. MSN still supplies optional personal local observations only; it is not used to invent OHLCV, fill missing history or update portfolios automatically. Active-record encryption and account synchronization remain outside this audit; encrypted backup downloads continue to work.
